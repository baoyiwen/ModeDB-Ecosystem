# Tests (`test/`)

DR-P4.6 preparation: `node --test --test-reporter=tap test/unit/security-device-drill.test.mjs`; native loopback/DPAPI/Named Pipe/visible Chrome smoke: `node scripts/security-device-drill.mjs smoke`. See [the two-Windows guide](../docs/security-v1/windows-device-drill-guide.md). Smoke uses a new synthetic instance and unique TLS key, never a virtual authenticator; it cannot complete actual Hello/two-device acceptance. No existing dist, local Vite/env, live configuration or 9091 is used. Actual A/B, hardware confirmation and recovery-policy exercises remain pending.

## Commands

`node scripts/security-performance-check.mjs explore`, then `register <exploration-report>` and `confirm <registration.json>`, runs the separate DR-P4.5 AB-BA server benchmark. It uses new Windows DPAPI/HTTPS instances, fixed synthetic data, software WebAuthn signatures, normal durable audit, single-client samples and a 48-request native pending-capacity flood with real OS-pipe policy apply/confirm/rollback. Stop other acceptance processes before measuring. Reports retain every sample, bind source/build/runtime and reject late/widened thresholds, missing metrics, skips or resource/repair overruns. CPU/RSS cover the server Node process; DPAPI child wall time is included but child CPU/RSS are unmeasured. The deterministic 4-active/32-waiting queue check uses a synthetic protector and is explicitly separate from native measurements. See the [performance guide](../docs/security-v1/performance-guide.md). This does not qualify production capacity or actual Hello/two-device behavior.

`pnpm run test:security:full` (or `node scripts/security-full-check.mjs`) runs DR-P4.4 on Windows with existing dependencies and Chrome. It discovers all unit test files, runs six engine flows in a new temporary cwd, builds three fresh frontends without local Vite/env, then requires nine candidate-browser and thirteen additional native integration tests. Missing summaries, failed commands, skips, timeouts or source drift fail acceptance. Strict Server/selected-test types, three-frontend types, SDK DOM consumers and browser boundaries are included. Data backup restore preserves V5 user disable and recipient history; portable recovery restores data with an empty access ledger and rejects old sessions/new proofs from old identities. Public outputs are scanned for bounded known secret patterns, supplemented by dynamic-material assertions; this is not a universal secret detector. No live instance, original dist or system trust is changed. This runner excludes independent performance and actual Hello/two-device acceptance: use the separate DR-P4.5 entry above; physical-device acceptance belongs to DR-P4.6. See the user guide's DR-P4.4 section.

## Layout

`pnpm run test:security:install` (or `node scripts/security-install-check.mjs`) runs DR-P4.3 with a fresh seven-package/three-frontend candidate, actual offline tarball installation, bin/CLI and strict Node/DOM consumers, then uses installed minified JavaScript for synthetic Windows DPAPI upgrade/disable checks. It verifies explicit V1→V5 migration, key/Token/session/revocation preservation, unknown-format rejection, signed login, registration closure, cross-restart user disable, fresh login after re-enable, recipient history and access reset. Designer hosting is HTTP byte/hash verification, not visual or hardware acceptance. The frozen V1 reader is transpiled with current installed helpers; it is not a complete historical release downgrade. Modules use independent Terser name scopes so a local Buffer binding cannot rename another file's global Buffer. `unit/security-install-contract.test.mjs` and `unit/security-install-evidence.test.mjs` cover this regression and false/missing evidence. No original dist, local Vite/env, live service/configuration, system trust or business data is used; temporary package artifacts remain local and may expire. The integrity checker validates archived reports and source hashes, not current artifact availability or a rerun of installation. See the release guide §2 and SEC-M7 / D31.

`pnpm run test:security:registration:integration` (or `node scripts/security-registration-integration-check.mjs`) verifies DR-P1.6 in nine required cases with a JSON report and complete TAP in a new temporary directory. It uses a fresh Chrome CDP virtual authenticator, synthetic HTTPS pin/DNS limited to that process, real Windows DPAPI/Named Pipe/CLI, private status without business sessions, proof/decision races, bounded admission and restart with registration disabled. Eight other flow cases use real WebAuthn verification plus a synthetic AES-GCM protector, including a real child hard exit at each atomic approval point. Capacity setup uses explicitly unverified synthetic rows; the browser exercises the actual final slot and overflow, not 1000 authenticators. It installs no system trust and reads no live configuration or data. Windows/Chrome are required, never silently skipped; the four report-parser tests reject incomplete or missing evidence. Virtual authentication is not Windows Hello, hardware provenance, public-key login, production UI, performance or a new two-machine acceptance. See the [flow guide](../docs/security-v1/device-registration-runtime-guide.md#6-注册审批全流程验收与故障报告).

`pnpm run test:security:registration` (or `node node_modules/tsx/dist/cli.mjs --test test/unit/security-registration-contract.test.mjs test/unit/security-device-registration-contract.test.ts test/unit/security-registration-storage.test.ts test/unit/security-registration-runtime.test.ts test/unit/security-registration-approval.test.ts`) verifies DR-P1.1—P1.5 deployment, public protocol, persistent storage and registration HTTP. It uses public synthetic certificates, request-local `.test` DNS and a random loopback TLS listener. The public schema tests cover version/field rejection, canonical origins, time/trust binding, decoded base64url limits, continuation secrets, state transitions and metadata-only audit/status responses. The 23 storage tests use fresh synthetic instances to cover disabled defaults, CAS migration, identity/key preservation, immutable associations, capacity, revocation/reset, six atomic-write fault points, actual child-process exit and Windows DPAPI. Windows tests are required, not silently skipped. The [frozen V1 reader](fixtures/security-registration-legacy/README.md) opens V1 but refuses V2/V3 without overwriting materials; this is not a complete old release installation/downgrade acceptance.

No OS trust store, real configuration or live 9091 service is accessed. `node scripts/security-registration-consumer-check.mjs` builds fresh shared declarations in a temporary directory, strictly consumes SDK types with DOM and no Node ambient types, and bundles shared/SDK for the browser without server/core/WebAuthn dependencies. `node scripts/security-registration-storage-check.mjs` checks the entire Server and strict storage/runtime/approval test types against fresh shared declarations, reusing installed common/core declarations without changing existing dist. `node scripts/security-registration-library-check.mjs --installation <isolated-folder>` checks the separately locked 14.0.3 library installation and malformed-proof rejection; see the [protocol contract](../docs/security-v1/device-registration-protocol-contract.md). Storage fixtures use random public-key bytes, not verified WebAuthn proofs or administrator approvals. The 22 runtime tests verify actual library processing of synthetic none responses, single-use persistent claims, origin/RP/UV rejection, private polling, expiry, bounded budgets/queue, write faults and native isolated DPAPI/HTTPS. The selected 25-package graph is now integrated into the Server/root lock and separately installed offline. The 21 approval tests cover OS-local identity, exact grants, atomic decisions/audit, CAS conflicts, expiry/terminal rejection, private approved polling without sessions, prior V2 missing grants, limits and commit faults. Real Windows DPAPI/Named Pipe/CLI list/approve/reject is required; the candidate fixture is trusted storage input, not an authenticator proof. Registration/approval vertical integration is covered by the separate DR-P1.6 runner below; login, real authenticators, release installation and performance/capacity acceptance remain future work. None attestation is not hardware or private-key possession evidence. Existing lint/format ignore rules still exclude `test/**`.

`node scripts/security-release-candidate.mjs` creates fresh temporary package and frontend outputs, verifies archive manifests and installs the exact local tarballs offline. Third-party code is snapshotted from the installed dependency tree; registry resolution and third-party lifecycle scripts are outside this check. `node node_modules/tsx/dist/cli.mjs scripts/security-release-verify.ts <release-candidate.json>` checks installed hashes and executes the real Windows synthetic lifecycle and legacy/registry performance comparison. Run performance alone, after other acceptance processes finish. `node scripts/security-release-regression.mjs` runs every unit test with its existing temporary fixtures, then runs all six engine integration scripts from a fresh temporary cwd so their relative `data/` paths stay outside the repository. Set `MODELDB_TEST_APP_ROOT=<ReleaseRoot>/apps` for both browser acceptance files to serve the three fresh builds. See the [release guide](../docs/security-v1/release-guide.md) for commands, scope and rollback boundaries.

Candidate frontend builds use allowlisted temporary source copies and freshly compiled workspace packages with `configFile: false` and `envFile: false`; local Vite configs, certificate setup and `.env` files are not loaded. `unit/security-release-apps.test.mjs` verifies this with a hostile synthetic config and sentinel env value. `unit/security-release-evidence.test.mjs` covers current/historical snapshot integrity, EOL-only development changes, tampering, skipped tests, incomplete newest evidence, duplicate paths, traversal and junction rejection. The full regression report now records test counts and fails on skips, cancellations, todos or missing counts.

`pnpm run test:security:recovery` builds the security packages and runs S6.1 recovery-package, JWE/WebCrypto interoperability, historical-key, process-interruption and isolated Windows CLI/DPAPI tests. It never uses the live service or repository configuration. Passing these tests does not constitute a second-machine recovery acceptance.

`pnpm run test:security:fault` builds shared/common/core/server and runs S7.1 reset recovery and audit flood acceptance. It covers the real Windows offline verify/resume/restore CLI, encrypted synthetic Vault recovery with an empty access ledger, reset/recovery process exits, hostile paths and changed files, bounded anonymous aggregation and samples, restart continuity, socket attribution under forged-header floods, audit capacity reservations, injected ENOSPC, and source-window/ban limits. All directories and configurations are synthetic and temporary. No live 9091, repository security state, physical disk exhaustion or hardware power loss is involved. See [reset recovery](../docs/security-v1/user-guide.md#61-出厂清除中断验证续跑或恢复副本) and [audit counting](../docs/security-v1/user-guide.md#21-高频拒绝事件的计数).

`scripts/security-recovery-drill.ts prepare|verify` provides a synthetic two-environment Windows acceptance drill. It transfers only an encrypted package, synthetic Vault and manifest, with the passphrase delivered separately. Same-machine/same-user verification fails, and editing the manifest cannot bypass the encrypted environment binding. See [SEC-M6 acceptance instructions](../docs/security-v1-deliveries/SEC-M6.md) for commands, ACL requirements and remaining evidence.

For repeatable manual runs, use `scripts/security-recovery-drill.ps1 -Action Prepare|Receive|Verify`. It builds the four required packages by default; `-SkipBuild` reuses existing outputs. The TypeScript runner creates fresh external session directories and non-overwriting, redacted reports with source/build fingerprints. `security-recovery-drill.test.ts` exercises the actual Windows PowerShell 5.1 wrapper, paths with spaces, independent-environment refusal, manifest tampering, incomplete input, error redaction and existing-file preservation. See [the two-device guide](../docs/security-v1/user-guide.md#41-两台-windows-设备的可重复演练脚本). Local tests do not count as a second-device success.

Run the manual drill and its Windows wrapper tests from a normal, non-elevated PowerShell. The wrapper checks the actual process token before building or creating directories and returns `RECOVERY_DRILL_NON_ELEVATED_REQUIRED` for elevated administrator tokens. Elevated file ownership can differ from the strict current-user ownership requirement; the drill does not rewrite ACLs to bypass that check. The token test checks the behavior appropriate to its actual Windows token; a non-elevated test run does not claim that an elevated child process was launched.

The wrapper reads Node JSON as UTF-8 and restores console/pipeline encodings after the call. Regression tests use actual PowerShell 5.1 with CP936 and a Chinese temp path, and exercise both TypeScript CLI entries plus the wrapper through a code-directory junction. Recovery-material junctions remain rejected; resolving a code entry does not relax recovery path validation. Sync all three `security-recovery-drill*.ts` files and the `.ps1` together on both devices.

If the supplied Prepare/Verify reports agree on the run and source but disagree on the build, run `node scripts/security-recovery-build-check.mjs`. It reads only compiled code, source-file existence, fixed compiler configurations and the installed TypeScript version, and writes a fresh temporary redacted JSON report with per-file hashes. It does not import server modules, read instance secrets, rebuild, remove stale artifacts or rerun recovery. `extra` is a missing-source diagnostic, not an automatic deletion list. See [the build comparison guide](../docs/security-v1/user-guide.md#42-构建摘要不同的诊断).

## DR-P3.1 同源托管与本机管理

可显式开启 `security.hosting`，同源 Designer/API 与专用 127.0.0.1 管理监听器分离；本机启动器无需手输 Token，管理 Cookie 空闲 15 分钟/绝对 60 分钟且无数据授权。静态内容启动时白名单快照，拒绝源码/秘密/路径穿越与链接，绑定失败不扩大监听范围。默认保持旧独立前端模式；正式注册/Passkey 状态页继续 DR-P3.2。配置、隔离命令、错误与验证见[手册](../docs/security-v1/device-registration-runtime-guide.md#12-同源页面与专用本机管理入口dr-p31)。

开发验证：`pnpm run test:security:hosting`、`node scripts/security-hosting-integration-check.mjs`；构建：`node scripts/security-hosting-build.mjs --output <new-directory>`。构建禁用本地 Vite 配置/env，原 dist 不覆盖；集成强制原生 Windows/Chrome，使用临时合成实例和随机回环端口，缺证据或 skip 不通过。复用现有三语言界面；Hello、LAN、新双机、生产性能与真实切换仍需后续验收。

DR-P3.2：`pnpm run test:security:designer-identity` 运行 SDK/页面状态安全边界与报告校验；`node scripts/security-designer-identity-check.mjs` 构建全新托管 Designer，强制原生 Windows DPAPI/Pipe、合成 TLS、随机回环端口、独立 Chrome 和虚拟认证器，操作实际页面注册/拒绝/批准/登录、描述导入、取消、刷新/注销及到期窗口/停用拒绝，并输出 zh/en/ja、1280/390 截图。它不安装系统信任、不读取真实配置/9091/业务材料，不代表 Hello 硬件、新双机、完整业务保存或生产容量验收。文档见[操作说明](../docs/security-v1/device-registration-runtime-guide.md#13-designer-注册与-passkey-登录dr-p32)。

DR-P3.3：`node node_modules/tsx/dist/cli.mjs --test test/unit/security-identity-admin.test.ts test/unit/security-identity-admin-report.test.mjs` 验证专用管理端权限、严格字段/CAS、元数据分页、HTTP 审计与审计满；`node scripts/security-identity-admin-check.mjs` 使用全新临时托管 build、原生 Windows DPAPI/Pipe、合成 TLS/随机回环端口及新 Chrome profile 验证实际审批、用户/公钥维护、换钥、会话撤销、冲突不重放及 zh/en/ja 宽窄屏截图。分页容量仅离线准备临时无公钥记录，正式注册限流不变。实际 Hello/双机与生产切换不在本项范围。

DR-P3.4：`pnpm run test:security:deployment` 验证严格部署字段、默认回环/注册关闭、证书/RP/期限/网段、文件及实例绑定、独占租约、一次性提交、审计满和提交中断；`node scripts/security-deployment-wizard-check.mjs` 实际操作本机向导、导入/下载、明确确认、过期禁止导出和原生 CLI，核对持久网络规则与身份保留，再启动合成 HTTPS。所有监听使用随机 127.0.0.1，保留候选的 0.0.0.0 配置而仅在测试启动覆盖 host。独立 Chrome/DPAPI/Pipe、zh/en/ja、1280/390 和表单对比度实际验收，不安装系统信任或修改真实材料。D26 新证据继承 D25 字节，不重写历史验收。


DR-P3.5：node scripts/security-public-clients-check.mjs 使用全新三个前端 build、临时 DPAPI/Named Pipe 实例、合成 TLS/Chrome 虚拟认证器，验收 Studio/Web 公共身份和业务库连接，回归三前端配对/应用凭据；全部监听显式随机 127.0.0.1。node scripts/security-registration-consumer-check.mjs 检查三个前端完整严格类型、SDK DOM 无 Node 消费及 shared/SDK browser bundle。报告要求全部消费者/支持语言/截图/精确计数，拒绝 skip、硬件或系统信任虚假声明；授权查询成功不等于完整业务保存或真实 LAN/Hello 验收。

`pnpm run test:security:browser-candidate` (or `node scripts/security-browser-candidate-check.mjs`) verifies DR-P3.6 on one freshly built Designer/Studio/Web candidate. Six sequential groups contain nine required native tests for hosting, formal identity and approval, deployment, old pairing/application credentials and hostile browser origins. All three public-key sessions insert a synthetic row, reject missing CSRF/cross-database requests and read it after reload. The manifest binds development inputs and new frontend outputs, checked before and after every group; no local Vite/env, old dist, live instance or installed OS trust is used. Raw TAP, manifest, JSON and screenshots remain in a new temporary directory. Missing prerequisites, changed source/build, failures, skip, cancel or timeout fail acceptance. The hostile case uses actual Chrome fetch/forms/sandbox/frames and wrong-RP checks, plus raw socket Host/proxy controls against the native server; it is not real DNS poisoning or LAN/Hello hardware evidence. Default hosting still serves Designer only; the other apps are synthetic same-origin substitutions in this test. See [operations and troubleshooting](../docs/security-v1/device-registration-runtime-guide.md#17-浏览器候选验收与操作排障dr-p36).

DR-P4.1 接收方密钥：`pnpm run test:security:recipients` 运行独立 RSA/OAEP 证明、版本/重放/限额、用途隔离、停用与重启、原子故障及本机 HTTP 边界。`node scripts/security-recipient-check.mjs` 强制原生 Windows/Chrome/DPAPI 与全新 Designer，实际导入公钥、下载挑战、离线 inspect/prove、登记/替换/退役与 zh/en/ja 宽窄屏；输出新临时目录，失败不跳过。只归档公开报告/构建/截图，不归档挑战回执、私钥或口令。按登记对象交付包与真实 Hello/两台设备仍由后续 DR-P4 验收。

DR-P4.2 离线交付：`pnpm run test:security:delivery` 覆盖准确接收方/用户/版本/指纹/CAS、停用/退役、V5 禁止 PEM 回退、审计/故障及报告完整性；`node scripts/security-recipient-delivery-check.mjs`（或 `pnpm run test:security:delivery:native`）强制 Windows DPAPI，两临时实例验证原 backup.v2、asset.v1/v2 导出与删除源后导入，拒绝错目标/私钥/篡改和旧确认重复发布，检查新目标密钥域及空访问台账。每次冻结源码并生成新临时报告/TAP，不修改原 dist，不读取真实材料，不归档业务包/私钥/口令。无页面改动；不代替发行安装、实际 Hello/双机或性能验证。
