## 2. 状态和交付规则

| 状态   | 含义                                   | 更新条件                                                       |
| ------ | -------------------------------------- | -------------------------------------------------------------- |
| 未开始 | 尚未开展任务开发                       | 初始状态                                                       |
| 进行中 | 已开始开发或修复                       | 登记实际开始日期和当前任务                                     |
| 待验证 | 已有可审查实现，必需验证尚未全部完成   | 标明缺少的验证、环境和复现方法，不能按完成交付                 |
| 完成   | 任务产物可用，必需检查通过，证据已登记 | 里程碑还需通过其全部验收项和通用交付门槛                       |
| 受阻   | 有明确条件阻止继续或完成验证           | 写明原因、已尝试方案、影响和恢复条件；不把依赖尚未开始记作阻塞 |

交付单位为 SEC-M1—SEC-M7。一个里程碑可以跨多次会话开发；中间进度或部分任务完成不称为完整里程碑交付。下一里程碑的实现依赖前一里程碑完成；资料准备和不依赖前项结果的只读检查可提前进行。2026-10-22 用户在知悉 S6.1 异机验收缺口后要求开始下一步骤，允许先开发 S6.2；S6.1 保持待验证，S6.2 的开发不替代该实测，也不解除 SEC-M6 完成门槛。2026-10-23 用户知悉当前进度后明确要求下一阶段开发，继续推进 S6.3；独立恢复实测门槛不变。

技术验收依据可复现结果和证据，不另设默认的逐阶段人工批准流程。若某项必须由特定设备或人员验证，缺少结果时只标为待验证，不把未回复当成通过。用户反馈单独登记，未反馈不写为“用户已确认”。验收发现缺陷后，重新打开对应任务与里程碑，记录对后续交付的影响。

“交付完成”不自动代表部署、发布 npm 包、推送远端、删除旧库或执行真实环境密钥轮换。实际切换按已有授权范围和切换清单执行；隔离测试不能作为已经替换现有环境的证明。

## 5. 各里程碑验收门槛

每项结果必须在对应交付报告中登记通过、失败或未验证，并附证据；有失败或必需项未验证时，该里程碑不能标记完成。SEC-M1—M7 的阶段研发验收均已通过，S7.2 的性能、全流程和可安装候选证据见 [SEC-M7 / D02](security-v1-deliveries/SEC-M7.md#d02s72-全流程回归与发布准备)。验收限于报告登记的 Windows 隔离范围；真实发布、服务切换、生产容量、物理磁盘耗尽及硬件断电没有被计为已验证。

### SEC-M1：密钥与 Vault 基础

- M1-A1：数据解密不读取或派生自 API Token；使用不同认证凭证不改变同一 Vault 的数据密钥。
- M1-A2：Windows 实际运行账号可正常解封；未授权账号、错误密钥或缺失记录明确失败，不自动覆盖或创建替代空库。
- M1-A3：新库写入、重启、重新打开可读；旧格式识别结果明确，拒绝时源文件保持不变。
- M1-A4：注入写入中断、磁盘满与认证标签损坏，证明有效版本或恢复材料仍然可用，提交状态可确定。
- M1-A5：格式包含必要版本、密钥引用和恢复封装契约；审计结构和错误码可供后续阶段使用，秘密不进入配置或诊断输出。

本次交付可验证引擎基础，尚不能宣称提供凭证轮换 UI、浏览器自动配对或独立灾备。

### SEC-M2：身份与凭证生命周期

- M2-A1：全新实例和并发启动只产生一致的实例身份；初始化中断可以恢复，安全台账独立于业务 Vault。
- M2-A2：只有符合 OS 身份/ACL 的本机管理客户端可执行维护；普通 loopback HTTP 请求不能抢占管理员或重置访问。
- M2-A3：创建、到期、轮换宽限、立即撤销和访问重置可通过 CLI 验证；原始凭证仅创建/轮换时交付，不可通过列表取回。
- M2-A4：撤销状态持久化并通知会话层；进程重启后不复活，维护凭证不重加密业务数据。
- M2-A5：初始化、凭证维护和访问重置从实现起记录脱敏审计；安全台账损坏或关键审计持久化失败不会静默放行敏感变更。

应用主体及会话失效机制在此完成；完整 HTTP/WS 入口接入分别在后续里程碑验证。

### SEC-M3：全入口统一授权

- M3-A1：已盘点入口全部接入统一身份/授权检查；默认拒绝，实例管理能力不泄露给普通数据凭证。
- M3-A2：限定接口凭证不能读取未发布字段、访问其他库、调用通用 RPC 或系统管理模型；发布范围扩大需重新检查权限。
- M3-A3：bind/unbind/rebind、级联、间接写入、导入导出和备份均有授权；批量事务无权限时回滚/拒绝，部分成功模式逐项反馈。
- M3-A4：HTTP、已有 WS 和缓存中的旧权限对新操作及时失效；进入提交阶段的事务保持约定一致性。
- M3-A5：应用后端可用限权服务凭证调用指定接口；伪造用户/角色/租户头不扩大权限，审计明确标记应用声明身份。

不以此宣称提供外部令牌交换或用户/租户行级隔离。

### SEC-M4：安全连接与 Designer 会话

- M4-A1：受支持部署可完成 HTTPS/WSS 或受信代理链路；证书错误、非 loopback 不安全配置和旧协议无静默降级。
- M4-A2：可信代理、IPv4/IPv6/CIDR 与名单执行有效；伪造代理头不能绕过来源规则或伪造可信来源。
- M4-A3：本机正常安装启动可配对进入 Designer；单次授权过期/复用失败；普通浏览器访问不能先到先得成为管理员。
- M4-A4：浏览器短期会话、注销、远程配对、Origin/CSRF 与撤销均可验证；前端产物和 Web 存储没有长期 Token。
- M4-A5：SDK 及标准 HTTP/Postman 调用都成功通过限权接口；展示完整地址，认证错误与版本错误明确，不按 SDK 声明决定放行。

S4.1 已完成：来源规则已有可验证执行入口，TLS/WSS、代理链、IPv4/IPv6/CIDR、Origin、查询参数凭据拦截和 SDK 安全端点均已覆盖隔离测试。S4.2 已完成可信管道启动器、Origin 绑定的一次性邀请、HttpOnly Cookie、CSRF、续期/注销及三个前端的 Chrome 验收。S4.3 已完成完整 POST 地址、Bearer/curl/Postman 模板、发布授权信息和 HTTP/SDK 一致性验收。完整可视化维护和日志检索在 SEC-M5 完成。

### SEC-M5：安全中心、日志与网络防护

- M5-A1：安全中心为完整页面，进入/返回保持编辑器上下文，权限可见性与实际授权一致，zh/en/ja 文案齐全且操作布局稳定。
- M5-A2：可按可信 IP、时间、主体、接口和原因查询数据安全日志；未认证/失败/成功访问分别统计，聚合次数与样本数不混淆。
- M5-A3：日志脱敏、受控查看/导出、保留/轮转及磁盘/队列告警有效；写入/关键管理逐项留痕，上游拦截不可见的边界有说明。
- M5-A4：管理面与数据面黑白名单分离，拒绝优先，允许名单开启但为空时拒绝；期限、重启、现有 WS、限流和临时封禁符合规则。
- M5-A5：网络变更命中预览、限时确认回滚和受保护本机修复可用；UI/CLI 行为一致；主密钥轮换可恢复，出厂清除具备目标校验、备份措施和破坏性确认。

S5.1—S5.3 已完成，M5-A1—M5-A5 通过。Windows 隔离安全回归 71/71、三个生产前端 Chrome 验收 1/1 通过；真实 DPAPI、HTTPS/WSS、OS Named Pipe 修复、UI/CLI 规则维护、IMK 轮换恢复与离线清除保护均有证据，见 [SEC-M5 / D05](security-v1-deliveries/SEC-M5.md)。清除中断会阻止启动，但未提供续跑/归档恢复工具；归档依赖同机同账号 DPAPI，独立恢复及 DEK 轮换仍待 SEC-M6。该里程碑不以某个 UI 按钮出现作为完成依据。

## 6. 每次交付的通用门槛

1. 任务表、里程碑状态和进度计数一致，所有验收项都有实际结果。
2. 交付报告说明对应代码/文档、构建版本或可确定的工作区状态；没有提交时不虚构提交 SHA。
3. 运行与变更相关的类型、构建和测试检查，记录命令、环境、结果和必要日志；浏览器、DPAPI 和异机恢复等实机结果不能用纯模拟替代。
4. 区分原有问题与本次缺陷；本次引入的问题、失败必需检查和缺失必需环境不得隐藏。适用的仓库规定检查同样需要完成。
5. 使用隔离目录和测试实例验证。真实业务库删除、进程切换、密钥轮换和外部发布不混入普通测试。
6. 脱敏交付证据：只记录凭证 ID、密钥 ID、统计与请求 ID，不把秘密、恢复包或业务明文放入仓库报告。
7. 尚未具备的后续能力明确列出，不能把单个阶段交付描述为整个安全系统已经完成。

不设置无法证明的性能承诺。性能门槛和可接受变化在首次基线测量后登记；后续新增失败、变更或未解决问题才要求扩大或重复验证。
